Progi trybu auto w libgen9blas_blas po userptr, 2026-11-12, UHD 620 (bez NEO, kcl), OpenBLAS pthread, 8 wątków sprzętowych.

Pytanie: od jakiego rozmiaru poziomy 1–2 na zwykłej pamięci (nie USM) opłaca się wysłać na GPU, skoro po userptr
(BEZNEO.md 6g) nie ma już kopii przez CPU? Kryterium (cel Karola: odciążyć CPU): czas CPU procesu na wywołanie
na GPU < czas CPU procesu w OpenBLAS (8 wątków = ustawienie domyślne programów; 1 wątek dla porównania).
Czas ściany raportowany obok -- nie jest kryterium, ale duża strata czasu ma być widoczna.

== PRZEWIDYWANIE (przed pomiarem) ==
Stałe: przypięcie userptr ~0,45 µs CPU/stronę [POM 6g]; jedno jądro bez NEO 36 µs / 7 µs CPU [POM 6c];
RAM GPU ~20 GB/s, CPU 1 wątek 17–18 GB/s [POM]; z Pythona gen9blas.axpy na tych samych tablicach 0,25 ms CPU,
z czego nakładka Pythona ~50 µs [POM/OPR].
[HIP] c0 = koszt CPU jednego wywołania GPU z C przez libgen9blas_blas na tych samych tablicach: 20–60 µs
      (execbuf + gen9blas/kcl: argumenty, wyszukanie userptr w pamięci podręcznej, budzenia nanosleep).
TRSV: ok. n/256 jąder -> c0 rośnie z n.

1. Te same tablice, poziom 1 (axpy 12 B/el.): OpenBLAS 1 wątek w LLC ~0,25 ns/el. -> próg n ≈ c0 / 0,25 ns ≈ 2^17;
   8 wątków (dzieli od n ~ 10^4, CPU ≈ 8 × ściana + wirowanie wątków) -> próg niższy, ~2^14–2^16.
   Dziś: zwykła pamięć zawsze CPU -> przewiduję zmianę na próg ~2^16 jak dla USM.
2. Te same tablice, poziom 2 (gemv 4 B/el.): 1 wątek ~0,13 ns/el. -> próg ~3·10^5 el. (n ≈ 550);
   8 wątków -> ~6·10^4 (n ≈ 256). Dziś 2^18 (n = 512) -> przewiduję obniżenie do ~2^16 jak dla USM.
3. Nowe tablice: przypięcie 0,11 ns/B danych wejścia ≥ koszt OpenBLAS 1 wątek (0,06 ns/B) -> GPU nie wygrywa
   z 1 wątkiem; z 8 wątkami w przybliżeniu remis. Prawdziwe programy w pętli używają tych samych buforów, więc progi
   ustalać według przypadku 1–2, o ile przypadek „nowe” nie jest drastycznie gorszy (> 2× CPU).

== POMIAR ==
bench/auto_thresholds.py (osobne procesy na tryb, 3 rundy na przemian, mediany; CPU wywołania = (CPU procesu w pętli
− CPU wątku głównego na przygotowanie danych) / R, więc wirowanie wątków OpenBLAS po wywołaniu jest wliczone).

Uwaga do metody: pierwszy przebieg był błędny -- OPENBLAS_NUM_THREADS ustawiane w procesie potomnym po imporcie NumPy
(NumPy ładuje systemowy OpenBLAS i ten od razu startuje 8 wątków), a scal z alfa = 1 OpenBLAS pomija. Poprawione:
zmienne ustawia rodzic, scal z 0,999, przerwa 0,2 s przed każdym przypadkiem (wirowanie wątków po poprzednim).

== WYNIK NA BATERII (typ S, 3 rundy; tabela pełna niżej) ==
- c0 (CPU wywołania GPU, te same tablice): 45–100 µs przy krótkim wywołaniu, rośnie do 200–300 µs przy wywołaniach
  > 1 ms (budzenia nanosleep w czekaniu), TRSV 170–570 µs. Przewidywanie 20–60 µs -- za nisko.
- OpenBLAS dzieli na wątki axpy (od n ~ 10^4), gemv, ger, symv, trmv, syr (od n = 128, czyli 2^14 el.): CPU ≈ 6–8 × ściana
  (wirowanie), np. axpy n = 16 384: 42 µs ściany / 331 µs CPU. Tu GPU odciąża CPU już od progu podziału OpenBLAS
  (iloraz CPU 0,05–0,3). Tego model nie przewidział (zakładał CPU ∝ dane).
- Nie dzieli (dot, nrm2, scal do 1M, copy, iamax, trsv): koszt CPU = ściana jednego wątku. GPU odciąża od:
  nrm2 2^16 (0,6), axpy 2^18, pozostałe 2^20 (0,2–0,5), trsv n = 1024 (te 0,30, nowe 0,98), n = 2048 (0,11 / 0,42).
- OpenBLAS 1 wątek, poziom 2: GPU odciąża od n = 1024 (2^20 el.: 0,4–0,65), przy n = 512 remis (0,85–1,4).
  Przewidywanie (2^16–2^17 dla poz. 1, ~3·10^5 dla poz. 2) -- za nisko, bo c0 wyższe, a OpenBLAS w LLC szybszy.
- Nowe tablice: przy 4M el. przypięcie ~3 ms CPU (0,37 µs/stronę) -- GPU = 1–1,3 × CPU jednowątkowego OpenBLAS
  (dot, copy, axpy); przy 2^20 el. jeszcze 0,25–0,5. Z 8 wątkami GPU wygrywa zawsze od progu podziału.
- Czas ściany: przy progu 2^14 (funkcje dzielone) GPU 2–5× dłużej; przy 2^20 równo (0,6–1,8×).

Wniosek (propozycja): jeden próg 2^20 el. (poziom 1: n, poziom 2: M·N) dla zwykłej pamięci, gdy OpenBLAS liczy jednym
wątkiem albo funkcja nie jest dzielona; 2^14, gdy OpenBLAS ma > 1 wątek i funkcja jest dzielona (axpy, gemv, ger, symv,
trmv, syr/syr2). Liczbę wątków można odczytać z OpenBLAS (openblas_get_num_threads).
