# Attention asm kernel through kcl on userptr memory in llama.cpp's KV layout (docs/attention-gpu.md section 10)
# Desktop "tc": HD 530 (i5-6500; Gen9 GT2, 24 EU, max 1050 MHz), production server (TV streaming ~30 % of one core);
# every command nice -n 19 + ionice idle + timeout; per launch <= ~90 ms. NEO 24.35.30872.36 for the NEO runs.
# Host programs: bench/attn_kcl.c (kcl + userptr, llama.cpp layout), bench/attn.c (NEO, device buffers; QTOK=1 = Q in
# llama.cpp's layout). Binaries: asm/Makefile attn, *_tok = template with -DQTOK (Q[t][h][d]); kcl table from the
# whl binaries (lib/gen_kernels.py with an explicit binary list), NEO runs with the skl binaries.
# Rates: 4 * n_q * n_k * H * d_head / time. Error: max |O - O_ref| / max |O_ref| vs FP64.

## Binary choice (laptop, before any GPU run)
skl and whl builds of attn_qwen / attn_llama (and *_tok) have byte-identical .text.k_attn, .text.k_kt, .ze_info,
.symtab and build options; only .note.intelgt.compat (the device id NEO checks) differs. kcl ignores that note, so
either runs on HD 530 through kcl; the kcl table uses the whl binaries (as lib/kernels.c does for the GEMMs).
QTOK binaries: same generated loop (1494 / 1475 lines, 1024 mads, 0 conflicts), only IGC's prologue differs; the
four existing hashes in asm/attn_sha256.txt unchanged.

## Step 1 predictions (written 2026-11-13 16:10 before the runs)
- Kernel-only rate through kcl + userptr: same ISA, V read from userptr in a sequential walk (~8 keys per 4 KB page
  per KV head, all threads within a few hundred keys of each other, so tens of pages at once, not hundreds):
  Qwen 285-296 GFLOPS, Llama 300-311 (0-4 % below NEO device buffers). QTOK vs the old Q layout under NEO: +-1 %.
- k_kt through kcl (SIMD32, local 256, K from userptr): 0.25-0.35 ms per layer at n_k 4096 (NEO 0.28).
- Incl. k_kt: -1 %; incl. submission + wait per layer (one execbuf + GEM_WAIT, ~50-150 us): another -0.1..-0.3 %.
- Verdict: PASS (>= 270 on Qwen incl. pre-pass), expected ~285-292.
- First use (pinning, 0.45 us CPU per 4 KB page): KV_SIZE 4096: 2 x 2 MB per layer = 1024 pages = ~0.5 ms per
  layer, ~13 ms for 28 layers (+ ~0.7 ms for Q/O 6 MB once); KV_SIZE 8192: ~0.9 ms per layer, ~26 ms. Steady state:
  no pinning (cache hits). REG=view (n_k rows) pins less the first time but re-pins whenever n_kv grows.
- OA vs the NEO run: EuStall 2-4 %, idle ~20 %, L3 110-120 GB/s, GTI read higher by at most a few GB/s (userptr
  pages are in the same LLC/RAM); no userptr page effect visible.

## Step 2 predictions: work-group size (written 2026-11-13 16:16 before the runs)
Model: a work-group's L/8 SIMD8 threads go to one subslice (8 EU x 7 threads = 56 slots), so the resident
fraction is floor(56 / (L/8)) * (L/8) / 56: L 8, 16, 32, 64 -> 100 %; 24, 48 -> 96 %; 96, 128 -> 86 %.
If the ~20 % idle EU time (Qwen) came only from this cap, 64 would beat 128 by up to 16 %; but the OpenCL C
variant A was 10 % slower at 64 than at 128 and LOCAL=24 was +3.5 % in one run, so a second factor (L3 reuse of
the K/V stream by the threads of a group, which run in lockstep over the keys) is expected to work against small
groups.
- Qwen (global 24576, valid L: 8 16 24 32 48 64 96 128): best at 24 or 48, +3..6 % over 128 (305-312 GFLOPS);
  32 and 64 within +-3 % of 128; 8 and 16 worse (-5..-15 %) with GTI read up; idle down where the cap rises.
- Llama (global 32768, valid L: 8 16 32 64 128): 128 best or 64 within 2 %; 8 and 16 worse.
- Grid order (all query rows of KV head 0 before head 1 vs interleaved): not run unless the counters show the
  work-group size is not the lever.

## Grid order prediction (written 2026-11-13 16:20 before the run; work-group size results are already in)
Variant HKV_INNER (template asm/attn.cl -DHKV_INNER): hkv = sg % HKV, so neighbouring subgroups (and the threads of
one work-group) walk different KV heads; default: all rows of head 0 first. Prediction: no gain; Qwen equal or up to
-3 % (two K/V streams per group instead of one, GTI read up), Llama (8 heads, 4 rows) -2..-6 %. Run with LOCAL 64
and 128 on NEO, alternating with the default order.
