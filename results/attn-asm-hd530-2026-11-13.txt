# Fused attention kernel in hand-scheduled Gen9 assembly, stage 2b of docs/attention-gpu.md (section 9)
# Desktop HD 530 (i5-6500; Gen9 GT2, 24 EU, max 1050 MHz), NEO 24.35.30872.36 (user space), nice 19 + ionice idle,
# 2026-11-13; background service ~30 % of one CPU core. GPU clock 1000 MHz in every run (sampled during the kernel).
# Same problem, host and error test as stage 2 (results/attn-kernel-hd530-2026-11-13.txt): one layer, non-causal,
# n_q 512, n_k 4096; Qwen2.5-1.5B shape H 12, H_kv 2, d_head 128; Llama-3.2-1B shape H 32, H_kv 8, d_head 64.
# Rate = 4 * n_q * n_k * H * d_head / time of the attention kernel (best of 5 after a warm-up); "incl. kt" adds the
# K-transpose pre-pass. Error = max |O - O_ref| / max |O_ref| vs FP64 (33 query tokens, all heads).
# Stop criterion (section 6): >= 265 GFLOPS on the Qwen shape (2.5x CPU 106) with error <= 2e-3.
# Build: asm/attn_gen.py (generator), asm/isa.py (operand parser), template asm/attn.cl, `make -C asm attn`
# (DEVICE=skl for HD 530, whl for UHD 620: a binary for one device is CL_INVALID_BINARY on the other).
# Run: CL=<file>.bin bench/attn <H> <HKV> <D> 512 4096 <RQ> <NK> (bench/attn.c now loads .bin with
# clCreateProgramWithBinary; the build parameters are baked into the binary and must match the arguments).
# All runs SIMD8, work-group 128, no spill. Bank conflict = src1 and src2 of a `mad` with the same register parity
# (asm/loop_analysis.py), counted per loop iteration (16 keys, 1024 mads).
# Note on the method: the predictions below were fixed before each measurement in the working notes; this file was
# assembled after the runs.

## Checks
- The driver runs our ISA: "poison" binary (one S mad with -q, otherwise IGC's code) -> error 7.75e-01 at the same
  speed; "plain" binary (IGC's code without .spv) -> same rate as the source (218.5 vs 215.5; 231.4 vs 230.8).
- Every generated binary below: error 1.96e-06 .. 2.14e-06 (FP32 accumulation as in stage 2).

## Variant 1 R: remap only (IGC's loop of bench/attn.cl variant A, operands changed)
Design: permute Q elements before the loop (64 single-float swaps) so every q element sits in a register of the
parity opposite to the K register it meets; p read from a copy of the other parity where V and p would conflict
(4 mov(8) per block, Qwen). Instruction stream otherwise IGC's.
Prediction: removes the conflict penalty (x0.8 on half the mads) -> at most +12.5 %: Qwen ~240, Llama ~260, if mad
issue is the limit; less if the loss is memory-side.
shape  conflicts before -> after   GFLOPS               error      clock
Qwen   512 -> 0                     218.3, 217.5 (plain 218.5)   2.05e-06   1000
Llama  512 -> 0                     245.2, 247.5 (source 234.6)  1.62e-06   1000
Reading: Qwen +0 %, Llama +5 %. Bank conflicts are not what holds Qwen; the stall is elsewhere (next variant).
ADV=0 diagnostic could not be remapped (IGC's ADV=0 build leaves no free register of the needed parity).

## Variant 2 S2: whole loop generated, ring of NS = 2 slots (template asm/attn.cl, PE_IN_S=0 COMPACT=0 sched2)
Design: IGC's prologue (Q load and scale, pointers, O = 0) and epilogue (O store) kept; IGC's loop is read by a
symbolic pass (registers of Q[r][c], O[r][c], K/V pointers, l sums, counter) and replaced. Per block of 16 keys:
16 K steps (2 block reads of 128 B -> 32 mads) then 16 V steps (2 block reads -> 32 mads), each into a slot of
8 GRF; the load for step s+NS is issued right after the mads of step s (1 step = 32 mads ahead, IGC: ~0). Softmax
between the phases: max by sel (8, 4, 2, 1), one uniform branch per row for the rescale, exp2 via math.exp, l in
FP32 lanes, p kept in an even and an odd copy; O /= sum(l) after the loop (IGC's l registers set to 1/8 so the
epilogue divides by 1). Conflict-free: slots start at even registers; Q permuted as in R.
Instruction budget per block (Qwen): 1024 mad, 64 send, 66 scalar :q header adds, 4 mov(8) S = 0, softmax per row
1 sel(8) + 3 scalar sel + cmp + jmpi + 2 add(8) + 2 math.exp(8) + 2 add(8) + 2 mov(8) (the 17 mul(8) + exp(1) of the
rescale run only when a row maximum grows), loop control 3: ~1190 issued instructions, 86 % mads.
Prediction: the IGC loop waits for each K/V load right before use; with ~6 threads per EU this leaves the EU idle
(ADV=0 268 vs 384 peak). Loads one step ahead should hide most of it. Ceiling: L3 read bandwidth, 8 B per SIMD8 mad
at RQ 2 (128 B feeds 16 mads); block reads with >= 2 in flight reach 155-158 GB/s on UHD 620 at ~1.1 GHz
(results/memory-bandwidth-2026-11-11.txt) = ~140-150 B/clk -> 280-300 GFLOPS at 1.0 GHz. Expected 250-290.
shape  conflicts   GFLOPS          error      clock
Qwen   0           287.7, 287.4    2.14e-06   1000
Llama  -           (does not fit: 16 even + 16 odd p registers for RQ 4)
Reading: +25 % over the template, criterion met (2.7x CPU). Prefetch was the missing piece; the C attempt (A2)
could not express it without spilling.

Purpose: free RQ*NK registers for a deeper ring (NS 4 = loads 3 steps ahead) and to fit Llama.
Prediction: NS 4 adds a few % if latency is still partly exposed; exp in place itself neutral.

## Verdict
Criterion MET. Best on HD 530 at 1.0 GHz: Qwen 295-296 GFLOPS (2.8x CPU 106), Llama 310 GFLOPS (2.9x CPU 107),
error 2.1e-6 / 2.0e-6. Predictions: R overestimated (no Qwen gain), S met at its upper end (288 vs 250-290),
C met (296 vs ~295).
What limits the best Qwen kernel: L3 read bandwidth. 296 GFLOPS = 18.5e9 SIMD8 mads/s x 8 B = 148 GB/s = 148 B/clk,
the block-read ceiling measured on UHD 620 (~140-150 B/clk) [EST: per-clock transfer to HD 530]. More speed needs
fewer bytes per mad, i.e. more query rows per thread; at d_head 128 FP32 Q and O already take 64 of 128 GRF for 2
rows, and SLM shares the same data port, so this is about the end for this design. Llama (4 B/mad, 78 B/clk) is not
bandwidth-bound; it is at 81 % of peak, limited by the non-mad instructions (~15 %) and the 4-row softmax.

## Hardening (review follow-up)
Changes (no kernel change in the loop): asm/attn_gen.py asserts that Q (permuted in place) is not read after the
loop in sched modes (as remap did), zeroes the whole send headers (K/V headers once before the loop; the epilogue's
O-store header r72 (Qwen) after the loop, since live analysis now treats partial writes as non-kills), fails on any
line of IGC's loop/epilogue that asm/isa.py does not understand (isa.check), asserts the heuristics (one l register
per row, accumulated once, read by the epilogue; exactly one cmp (lt), counter written only by cnt += 8*NK, limit
not written, exit on the cmp flag), asserts NS <= D/8 and reports the Kt over-read; pins ocloc 24.35.30872.36.
bench/attn.c: Kt padded by KT_PAD = NK*D*16 B (was +64 KB; over-read is 2560 B Qwen C4, 1280 B Llama C2), n_k,
LOCAL and full-subgroup checks (error, not a silent local = 8), reference sample STEP 7 by default (STEP 16 visited
only rows 0-5 of each 32-row work-group), STEP=1 = whole output; K/V converted to double once (STEP=1 takes ~8 s).
asm/Makefile: attn-check (skl + whl rebuilt, SHA-256 vs asm/attn_sha256.txt, part of `make check`), DEVICE stamp.
Binary diff vs. commit 12a3e24 (asm compared): only 4 (Qwen) / 3 (Llama) `(W) mov (8) rH:ud 0` header zeroings
before the loop and 1 after it (Qwen: r72); register allocation and the loop body identical.
