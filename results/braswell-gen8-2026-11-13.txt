# Gen8 (Braswell / Cherryview) performance, 2026-11-13 -- the first measurements on Gen8 (docs/gen8.md 6d)
# Machine: Intel HD Graphics 400 (Cherryview, PCI 0x22b1 rev 0x35, 12 EU = 2 subslices x 6, 200-600 MHz), Celeron N3010
#   (2 cores), one DDR3-1600 module (single channel, 12.8 GB/s theoretical), Linux 7.0.0-43, i915, Python 3.14.4,
#   NumPy 2.3.5 with the reference (netlib) BLAS -- no OpenBLAS. Code at a3cd39a (main); lib/kernels.c md5
#   02e260eb5c20ceabb31ea0335da2255e, lib/kernels_gen8.c md5 ec61c822524c001356b178265c3ecac9 (ocloc 24.35 -device bdw).
# Background load on the machine: 2-core load 1.4-2.0 before each stage; every stage at nice 19 / ionice idle,
#   OPENBLAS_NUM_THREADS=1, started only below load 2.5. GPU clock sampled every second during the runs: GEMM stages at
#   600 MHz (240 s; 8 s at 200), level 1-2 mostly idle between calls (12 s at 600, 19 s at 200); hottest core 64-65 C.
# Peaks at 600 MHz (CHV PRM vol04 p.5): FP32 115 GFLOPS, FP64 14.4 GFLOPS.

## Summary
# - SGEMM (sgemm_v from OpenCL C, Gen8 packing layout): 42.3 / 40.5 / 38.0 / 36.2 GFLOPS for n = 1024 / 2048 / 3072 / 4096,
#   i.e. 0.31-0.37 of the FP32 peak (the UHD 620 asm kernel reaches ~0.8). FP16 not available on Gen8 (nan columns).
# - DGEMM (dgemm_v): 8.1-8.2 GFLOPS (0.57 of the FP64 peak), the same in both rounds; n = 4096 takes 16.9 s.
#   est_ms in lib/gen9blas.c assumes 8 GFLOPS (FP64) and 50 GFLOPS (FP32) for band splitting: FP64 matches, FP32 is about
#   1.2-1.4x optimistic (bands up to ~140 ms instead of 100 ms; harmless with one request per kernel).
# - Levels 1-2 ("GPU usm" column = data in gen9blas.empty memory, "GPU copy" = plain NumPy arrays): streaming routines
#   7-8 GB/s (0.55-0.63 of 12.8 GB/s); ger/syr/syr2 1.9-5.4 GB/s, trsv 3.5-4.5 GB/s, symv 9.7-12.1 GB/s (the script
#   counts the bytes of the formula, symv reads the stored triangle once). The "CPU (NumPy)" column uses the reference
#   BLAS on one Celeron core and is not a meaningful CPU comparison; "-" = no SciPy on this machine.
