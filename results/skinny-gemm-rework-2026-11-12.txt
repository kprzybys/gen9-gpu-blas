Rework of skinny GEMM A·Wᵀ (weights contiguous along K), 2026-11-12, mains power. Starting point: commit 40a71dc
(skinny_k1/k4/k8, FP16 block reads). Criterion (docs/roadmap.md): FP16 4096² M ≤ 8 ≤ 1.8 ms, M = 16 ≤ 3 ms, no regression for M = 1.

== DIAGNOSIS FROM ASSEMBLY (lib/.kernels/p3.d/.text.skinny_k4_h.asm, block path) ==
- Loop: 165 instructions for 64 useful FMA (16 dot4): mad 48, mul 32, mov 48, add 25, send 8.
  * dot(w, a) + s is not fused into the accumulator: mul + 3 mad + add per dot4 instead of 4 mad;
  * mixed operations hf->f (mov, mul) Gen9 splits into 2 × SIMD8 (mixed-mode restriction);
  * conversions: 4·(RW+MT) per pass.
- Thread: K = 4096, 16 subgroups per group every 64 k -> only 4 loop passes; prologue ~118 instructions, epilogue ~316
  (sub_group_reduce_add per accumulator, SLM writes, barrier, accumulation of 16 parts).
  Total ~1100 instructions per thread, of which ~256 useful mad -> ~25% of FMA peak. Measurement: 110–120 GFLOPS = 27–29%
  of 410 [MEAS]. The model (instruction cost, not memory) explains the measurement.
- A traffic from L3 = (N/RW)·M·K·e: k8 (RW = 2) at M = 16: 268 MB -> 1.7–2.3 ms at 116–156 GB/s (block read from L3 [MEAS]).

== VARIANT (one): skinny_r<MT>, SIMD8, RW = 8 weight rows, S = 4 subgroups per group ==
- SIMD8: float per lane = 1 GRF (in SIMD16 = 2) -> 64 accumulators (RW·MT = 8·8) fit in 128 GRF; mixed mode
  hf->f natively SIMD8 (no splitting). A lane reads 8 B (FP16: 4 k, FP32: 2 k) -> a 64 B message = 1 line.
- Accumulation with explicit fma per component (no dot), conversion component by component (fewer live registers).
- S = 4 subgroups every 8·KL k, stride 32·KL: K = 4096 FP16 -> 32 passes (was 4); 2048 threads at N = 4096 (margin
  over 168 hardware threads, tail ≤ 1/12).
- Epilogue: transposed reduction in the subgroup (shuffle_xor, 64 -> 8 values per lane, lane = weight row), then
  SLM [4][64], barrier, 32 work-items sum 4 parts each. ~300 instructions per thread vs ~32 × 340 in the loop (< 3%).
- Block path only: sak = 1, K % (32·KL) = 0, 16 B alignment; otherwise the old kernels. M = 1 stays on skinny_k1.
  MT = 4 for M = 2–4, MT = 8 for M = 5–16 (M > 8: tiles of 8, the M tile varies fastest in the grid -> second read of weights from LLC).

== PREDICTION (FP16, N = K = 4096, USM) ==
Loop (SIMD8, MT = 8): 256 mad + 64 conversions + 16 send + ~10 addresses/loop -> ~77% of the instructions are FMA;
MT = 4: 128 / (128 + 48 + ~10) ~ 70%. Latencies and occupancy [HYP] 0.7–0.9 -> F ≈ 200–285 GFLOPS (MT = 8),
180–260 (MT = 4).
Traffic: weights 32 MB from RAM (22–25 GB/s -> 1.3–1.5 ms); A from L3: (N/8)·M·K·2 = 4 MB·M... M = 8: 32 MB, M = 16: 64 MB (< 0.5 ms).
  M = 2–4:  max(1.3–1.5 memory; 0.5 compute)            -> 1.4–1.7 ms  (today 1.9–2.0)
  M = 8:    max(1.3–1.5; 268 MFLOP / 200–285 = 0.94–1.34)   -> 1.4–1.8 ms  (today 3.1)
  M = 16:   537 MFLOP / 200–285 = 1.9–2.7 ms (+ second read of weights from LLC, overlaps) -> 2.0–2.8 ms (today 4.9)
FP32: weights 64 MB -> 2.6–2.9 ms for M ≤ 8 (memory), M = 16: 2.6–3.0.
Risk [HYP]: S = 4 with RW = 8 is ~42 groups × 8 rows = ~340 read streams at once (today ~20) -- if M = 2–4
does not reach 20+ GB/s of weights, the model gap = number of streams (microbenchmark: row-wise gemv with different number of rows per group).
Risk: spill (gen_kernels.py will reject) -> then RW = 4 for MT = 8.

== PROCESS ==
1. First version (S = 4, FP16 ushort4): assembly of the FP16 r8 block loop: 293 instructions, 256 mad (87%) -- conversions
   hf->f went into mixed-mode mad (better than the predicted 77%).
2. skinny_r8 computed wrongly through kcl (weight rows 0–3 = sums of row r + 3), correctly through NEO: float s[8][8] (256 B per lane)
   IGC placed in private memory (private_size 2048, per_thread_memory_buffers scratch); s[8][4] (128 B) went
   to registers. kcl does not configure scratch. Fix: separate vectors s0..s7 (float8). Explicit unroll counts did not help.
   gemv_n/gemv_nw also declare private_size 256, but do not touch scratch -- so the generator does not reject private_size alone
   (to do: checking scratch accesses in asm).
3. Spill in FP16 r8: raw ushort4 = 1 GRF per component; the fallback path without alignment (2 B reads) in the same
   kernel spilled registers. Alignment is now checked by the host (the GPU address has the same offset within a page as the host:
   USM, kcl userptr; working buffer aligned); raw data as uint2.
4. Measurement S = 4: compute fast (FP16 M = 16: 167–208 GFLOPS), but weights only 14–18 GB/s for M = 2–8 (time
   independent of M) -> the risk from the prediction confirmed. S test (subgroups per group = bytes read contiguously from a row per
   group step): FP32 S = 4/8/16 -> 4096² M = 2: 4.06/3.89/3.50 ms, 11008×4096: 10.3/9.4/7.9 ms (22.8 GB/s);
   FP16 KL = 2 (32 B per message) smaller gain; FP16 KL = 4 (uint2, 64 B) S = 16: M = 2 1.58 ms (21 GB/s).
   Choice: S = 16, KL = 8 B per lane (FP16 4, FP32 2), MT = 4 for M ≤ 4, 8 for M > 4 (MT = 4 for M = 8 not better).

== PREDICTION VS MEASUREMENT ==
- FP16 4096²: M = 2–4 1.55–1.68 ms (predicted 1.4–1.7) -- hit, but only after S = 16; M = 8 1.9 ms (1.79–2.17;
  predicted 1.4–1.8, criterion 1.8) -- close, not met; M = 16 3.19 ms (predicted 2.0–2.8, criterion 3) -- no.
- Compute: 168–225 GFLOPS at M = 16 (predicted 200–285) -- lower bound.
- Model gaps:
  (a) weight bandwidth depends on the bytes read contiguously from a row per group step (S·64 B): 256 B -> 14–18 GB/s,
      512 B -> ~19–20, 1 KB -> 21–24 [MEAS]; the old kernels read 2–4 KB;
  (b) with long rows (44 KB) and 8 rows per group the bandwidth drops (FP32 K = 11008: 16–17 GB/s) [HYP pages/TLB];
  (c) M = 8–16: time closer to the sum t_mem + t_comp than to the maximum (4096² FP16 M = 8: 1.4 + 0.64 ≈ 1.9-2.0 ms) -- the thread
      loads, waits, computes; too little overlap [HYP]. Direction: earlier loading (registers: with 64 accumulators there is no
      room for a double buffer), A in SLM (frees 16 GRF for a double weight buffer).
