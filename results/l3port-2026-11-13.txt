# L3 / data-port ceiling and the Qwen attention loop (2026-11-13). Kernel bench/l3port.cl, scripts bench/l3port.sh,
# bench/l3port_oa.sh. Question (docs/attention-gpu.md section 8, "What limits it now"): is Qwen attention (8 B of
# block reads per SIMD8 FP32 mad, ~305 GFLOPS = ~152 GB/s on HD 530 at 1.0 GHz) bound by the data port / L3?
#
# Setup: 2048 SIMD8 subgroups, each streams n = 4096 OWord block reads of 128 B (L3-resident 64 KB region unless
# noted), MADS FP32 mads per block on the block's data (operands from adjacent registers: no bank conflict), PF
# blocks in flight per thread (refill right after use), addresses advanced by adds only (~3 non-mad instructions per
# block, as in the attention loop). Gop/s = GB/s of block reads; GFLOPS = GB/s x MADS / 8. Best of 5 launches.
# MADS 16 = the Qwen ratio (16 mads per 128 B block).
#
# History: two earlier versions were discarded as artifacts of the kernel, not the hardware: (1) IGC rotated the
# prefetched blocks with ~25 movs per 2 blocks and the mads hit src1/src2 bank conflicts; (2) the address took an
# integer multiply per block. Both made the mixed points issue-bound at ~240 GFLOPS (OA: FPU 93-96 % of active,
# stall 3-5 %). Raw output of all three versions: in this session's scratchpad, not kept.

## Reading
Port ceiling [MEAS]: HD 530 170-176 GB/s at 1.0 GHz = 7.1-7.3 B/clock/EU; UHD 620 199-200 GB/s at 1.1 GHz =
7.6 B/clock/EU. Same with work-group 64 or 128, PF 2 or 4, a 1 MB region (beyond L3) or 8 subgroups sharing a
sequence. Reached up to MADS 12 (the mads hide under the reads). The older 156 GB/s (results/memory-bandwidth-
2026-11-11.txt, k_owb2 on kp-laptop) is not the ceiling.
Qwen ratio (MADS 16): HD 530 146-153 GB/s = 293-306 GFLOPS, the same as the real loop (296-305), with OA showing
EU active 88-91 %, stall 4.5-6 %, both FPU pipes busy 95 % of active time: issue-bound, not port-bound. A
two-bound check agrees: time(MADS 16) 7.0-7.3 ms = the issue line through MADS 24/32 (12.46 ms - 16 x 0.333 =
7.1 ms), while the port alone would allow 6.2 ms.
So Qwen attention is NOT limited by the data port: the port runs at ~86-88 % of its ceiling. Removing non-mad
instructions helps until the port binds at ~172 GB/s = ~344 GFLOPS (90 % of peak) on HD 530 for 8 B per mad.
OA L3ShaderThroughput is accurate once scaled by clock: OA averages over its reports at 933-943 MHz; 171 GB/s at
1.0 GHz x 0.933 = 159.5 vs the counter's 159.1 (MADS 0); MADS 16: 137.6 expected vs 134-138 (97-100 %).
Open: the real Qwen loop shows 112-118 GB/s on this counter while its arithmetic gives 148 GB/s at 296 GFLOPS;
with the counter now calibrated, either the OA run had a lower clock / rate than the timed run or the loop reads
fewer bytes than counted. To check by the attention session (same OA run with the clock and GFLOPS printed).
The multithreaded model (results/mt-model-2026-11-13.txt) fitted an effective 6 B/clock/EU "port" limit: the fit
holds, but the measured port is 7.1+ B/clock/EU, so what the model calls the port stands for issue overhead and
latency effects together, not for the data port alone.
