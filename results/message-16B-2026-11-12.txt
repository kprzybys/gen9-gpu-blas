Access width per lane vs bandwidth (weaknesses from the ViennaCL test), 2026-11-12, mains power, USM, 1 CPU thread.

== STATE AND HYPOTHESIS ==
Measurement (vectors 10^7, gemv 3840²): COPY FP16 13.4 / FP32 23.4 / FP64 17.2 GB/s; AXPY 20.2 / 22.6 / 22.2; gemv N (rows)
FP64 21.9–23.2 GB/s (ViennaCL 25.3), the gemv_n/gemv_nw variant irrelevant (±5%), FP16 ~15.
ISA (ocloc disasm, copy_d and axpy_d): the same messages -- untyped surface read/write xyzw (16 B per lane), two per
4 FP64 elements (32 B per lane). Hypothesis: a SIMD16 message should cover contiguous full 64 B lines, i.e. 16 B per
lane: at 32 B per lane each of the two messages covers half of every line (write without a prior read ->
line refetch, ~1.5× traffic: 23.4/1.5 ≈ 16 GB/s, measured 17.2); at 8 B per lane (FP16) a message is only 128 B.

== PREDICTION ==
1. COPY with 16 B per lane in every type (FP16: 8 el., FP32: 4, FP64: 2): FP64 and FP16 ~23 GB/s (like FP32).
2. row-wise gemv (gemv_nw) with 16 B per lane: FP64 22 -> 24–25 GB/s, FP16 15 -> ~20 GB/s; FP32 unchanged.

== RESULT ==
ViennaCL test (medians of 3 runs, GB/s): dCOPY: 17.4 -> 23.6; hCOPY: 14.2 -> 21.2; dGEMV-T: 21.6 -> 24.1; hGEMV-T: 15.4 -> 16.5; sCOPY: 23.2 -> 23.5; sGEMV-T: 23.0 -> 23.3.
1. COPY 16 B per lane: FP64 17.4 -> 24.2 GB/s (prediction ~23: hit). FP16 with the copy16_h kernel (8 el., 16 B): only
   16.1 -- ISA: SIMD8, 8 × "byte gathering read 32b" (the compiler splits vload8 half into byte reads of 4 B, as in
   packing, docs/performance-model.md). Copy does not depend on the type -> FP16 (n even, addresses aligned to 4 B) goes through the FP32 kernel
   (n/2 words): 22.0 GB/s. Correctness: n even/odd, slices shifted by 2 B, USM and plain.
2. row-wise gemv 16 B per lane: FP64 21.6 -> 24.3 (prediction 24–25: hit; ViennaCL 25.3). FP16 with 8 el. per
   lane: 15.4 -> 11.1 (the same compiler problem) -> FP16 stays at 4 el. (8 B): 15–16.5 GB/s.
3. Review: the other level 1–2 kernels first read the destination vector (axpy, scal, rot, swap), so partial line
   writes affected only copy. GEMM: the epilogue is a small fraction of the time (FP64 1976³ compute-bound).
4. Bug along the way (caught by test_level12): the host computed the number of work-items as 16/element bytes, but the FP16 kernel has 4
   elements -- FP16 copy with odd n copied half; fixed (gw = GW from level12.cl).

gemv today 15–16.5 GB/s vs 22–24 in FP32/FP64.

== STEP 1 (later 2026-11-12): FP16 gemv with block reads -- PREDICTION ==
intel_sub_group_block_read_us8: a subgroup reads contiguous 256 B with one block message (OWord block), so the compiler
will not split it into byte reads; a lane gets elements every 16 (order irrelevant for the dot product).
Condition: address aligned to 16 B (checked once per group; otherwise the old path). Applies to row-wise gemv (gemv_nw,
mode 0 = full matrix). Prediction: FP16 row-wise gemv 15–16.5 -> 20–23 GB/s (like FP32).
== STEP 1 -- RESULT ==
row-wise FP16 gemv (gemv_nw, block read us8): 3840² 21.8, 4096² 20.7, 4096×11008 25.2 GB/s (was 15–16.5;
prediction 20–23: hit). FP16 gemv T (new gemv_t1b, block read us4, lane = columns every 16): USM 19.6–23.2
GB/s (was 15.4), plain 15.4–17.1. Small/odd sizes (1000², 4099×17) take the regular path. Errors 2–5e-4 as before;
test_level12 OK. Conclusion for the model: for FP16 block reads (intel_sub_group_block_read_us*) bypass the compiler's byte reads.
