# Status and roadmap

State of the library, its known limitations, and open work. Evidence tags as in `results/*.txt`: [MEAS] our measurement,
[SW] software behaviour fixed for a given driver/compiler version, [HYP] unconfirmed hypothesis.

## Current state

Implemented ([api.md](api.md)):

- **Level 3** in FP16 (fast and accurate), FP32, FP64: GEMM (transposes, any M, N, K), strided batched GEMM, SYMM, SYRK, SYR2K,
  TRMM, TRSM (FP16 / FP32 / FP64). GEMM main loops for FP16, FP16 accurate and FP32 are hand-written Gen9 assembly
  (`bench/gen_h.bin`, `bench/gen_hd.bin`, `bench/gen_s.bin`, regenerated by `make -C asm` from the frozen templates in `asm/`);
  FP64 is OpenCL C. SYRK / SYR2K / TRMM / TRSM pack the data once and run several kernel launches on fragments with a
  triangular epilogue, entirely on the GPU.
- **Skinny GEMM** (min(M, N) <= 16, no packing, FP32 accumulation): 1.3-6.9x faster than the packed path
  ([skinny-gemm.md](skinny-gemm.md)).
- **Levels 1-2** in FP32, FP16 (computed in FP32) and FP64, including banded and packed matrices; `rotg` / `rotmg` on the CPU.
- **BLAS/CBLAS drop-in** `libgen9blas_blas.so` (393 symbols, 110 on the GPU, the rest forwarded to OpenBLAS) with automatic
  CPU/GPU selection by measured thresholds.
- **No NEO**: `lib/kcl.c` submits command buffers straight to i915 ([no-neo.md](no-neo.md)); NEO builds remain for comparisons.
- **Zero-copy**: ordinary process memory through i915 userptr, USM host memory with a pool in Python, slices and `.T` views
  without a copy.
- Python wrapper `lib/gen9blas.py`; eight test suites (`make -C lib check`).

Comparisons with other libraries (CLBlast, OpenBLAS, OpenVINO, oneDNN, ggml Vulkan, ViennaCL) are summarized in
[benchmarks.md](benchmarks.md): at n >= 2048 `gen9blas` is faster than CLBlast in all FP32 and FP16 cases (FP32 4-12x, TRSM

## Known limitations

- Hardware: no INT8 dot-product instruction (DP4a), no matrix units; FP64 is 4x slower than FP32; the GPU shares RAM with the
  CPU and is memory-bound at ~20-25 GB/s, so levels 1-2 are limited by bandwidth ([hardware.md](hardware.md)).
- Only Intel UHD Graphics 620 (Whiskey Lake GT2) with Linux i915 has been tested. `kcl` submits command buffers directly; a bug
  can hang the GPU. It needs access to the render node.
- Complex types (C, Z) are not implemented on the GPU; the BLAS layer forwards them to OpenBLAS. Also forwarded: `rotg`,
  `rotmg` (computed on the CPU), Fortran level 1, `sdsdot` / `dsdot`.
- TBSV / TPSV are sequential on the GPU (one work-group, row by row), 6-40x slower than the CPU; the BLAS layer runs them on the CPU.
  TRSV is blocked (256 rows) and still slower than one CPU thread at n = 8192; the driver is busy submitting the many kernel
  launches (CPU 15-19% of a core after blocks of 256 replaced blocks of 64).
- LAPACK inside OpenBLAS (`np.linalg.solve`, `scipy.linalg.solve_triangular`) calls its BLAS directly and is not intercepted by
  `LD_PRELOAD` ([api.md](api.md)).
- SGEMM is ~4x less accurate than OpenBLAS / OpenVINO (relative error 1.6e-8 against 4-5e-9) because the FP32 tile sum is not split.
- Small sizes (n <= 1024): fixed call cost and packing make OpenBLAS 1.7-3x faster in SYMM / SYRK / TRMM / TRSM; for FP16 at n = 1024
  the oneDNN kernel without packing (3.1 ms) is faster than the whole `gen9blas` call (4.8 ms, of which the kernel is 2.98 ms).
- Skinny GEMM: FP16 M = 8 (1.90 ms) and M = 16 (3.19 ms) at 4096 x 4096 miss the 1.8 / 3 ms targets; M between 16 and ~256 is
  served by the packed assembly path, which repacks the weights on every call.
- Kernels with register spills would compute wrong results through `kcl` (no scratch support); the generator rejects them
  ([pitfalls.md](pitfalls.md)).
- Results of the benchmarks depend on power state: they were taken on mains power; on battery the CPU cost of calls is 2-3x higher.
  Run-to-run scatter is about +-10%, so comparisons should alternate runs.
- Zero-copy through userptr pins pages (~0.45 µs of CPU per 4 KB on the first use of an array, IOMMU cost), limited by `KCL_USERPTR_MB`.
  Writes to one cache line through two different GPU addresses are lost, and an object wider than the array fails with `EFAULT`
  (handled in `kcl_userptr`: overlapping regions of one operation share one object, exact ranges only).

## Open work

### Accuracy and small sizes

1. **SGEMM accuracy.** Target relative error <= 5e-9 (now 1.6e-8) with at most 5% loss of speed, by partial sums over chunks of K
   (as the accurate FP16 variant `GEN9BLAS_HS` does) or shorter sums within a tile. Analysis first, with a numeric prediction.
2. **Small sizes (n <= 1024).** The packing of FP16 was already made faster (HGEMM n = 1024: -8-10% time, HSYMM / HSYRK / HTRMM
   -13-15%); waiting was ruled out as the cause; FP32 gained nothing. Remaining: ~0.4 ms outside the kernels (submission, flush,
   wake-up) and 0.67 ms of packing. Further progress needs a kernel that works without packing (substantial assembly work).

### Skinny GEMM ([skinny-gemm.md](skinny-gemm.md))

3. Overlap loading and computing for M = 8-16: keep A in local memory, which frees 16 GRF for a double buffer of weights.
4. Microbenchmark of weight bandwidth (bytes read contiguously per group step, row length, number of rows per group) to derive
   the 16 KB row limit from a model instead of from measurements [HYP: pages / TLB].
5. The same rework for `A·B` (`skinny_n4`: weights read ceil(M/4) times, A traffic).
6. Detect real scratch accesses in the generated assembly in `lib/gen_kernels.py`; a non-zero private size alone is not enough
   (the GEMV kernels declare one and never use scratch).
7. Packed weights kept between calls (constant weights, as OpenVINO does) would remove the packing cost for M between 16 and 256.
   This is not a BLAS operation (the library cannot know that the data did not change), so it needs an explicit API or belongs to a
   separate AI library built on these kernels, together with INT8 / Q4 quantization, softmax, layer norm and a ggml backend.

### Performance of existing routines

8. DGEMM in assembly (now 55 GFLOPS, FP64 peak 90-94, OpenBLAS CPU 71-83): `asm/gemm_gen.py` knows only `mad` (16) for FP16 / FP32;
   FP64 is `mad` (8) with shuffles, so it needs a new template and loop analysis.
9. Levels 1-2: faster reductions (`dot` / `nrm2`), `axpy` in FP16, GEMV FP16 against FP32 (13-15 vs 22 GB/s was measured before the
   block-read variant), the ~50 µs gaps between TRSV kernels, fewer TRSV launches with larger blocks, and the ~50 µs of Python
   wrapper overhead per call.
10. Dependencies between kernels in one command buffer instead of a barrier after each (fewer GPU stalls).
11. Type conversion (`astype`) on the GPU in `gen9blas.py`; it runs on the CPU today.
12. Measure levels 1-2 of the no-NEO build against the NEO build (only level 3 has been compared in full).
13. GPU frequency: at 500 MHz levels 1-2 use the same energy as the CPU (0.26-0.35 J/GB) and GEMM uses 40% less energy for 2.2x the
    time; at the default 1100 MHz a memory-bound kernel keeps the GPU at 100% busy and loses energy efficiency. The library does not
    change the frequency.
14. Boot parameter `intel_iommu=igfx_off`: page pinning without the IOMMU might lower the userptr cost; its effect on GPU
    memory bandwidth is not measured.

### Upstream bug report (planned)

**compute-runtime (NEO 24.35.30872.36, Gen9, Linux 7.0 i915): instability with `CL_MEM_USE_HOST_PTR` on ordinary host memory.**
Observations (all [SW]; a minimal reproducer has not been written yet):
1. A zero-copy buffer (`CL_MEM_USE_HOST_PTR`) that overlaps another region of the same memory with a different size, also one
   copied by `clEnqueueWriteBuffer` in the same call, aborts the process at `host_ptr_manager.cpp:252`. Reading results with
   `clEnqueueReadBuffer` into a stack array registers the stack pages and fails the same way on later reads of a different size
   to the same place.
2. Buffers re-created over the same pages fail non-deterministically: `DRM_IOCTL_I915_GEM_EXECBUFFER2` returns `ENOSPC`,
   assertions at `host_ptr_manager.cpp:252` and `reference_tracked_object.h:134`, segfaults. Core dumps show the main thread in
   a wait and a NEO thread in `DRM_IOCTL_I915_GEM_WAIT`: NEO closes GPU objects asynchronously, and a new buffer over the same
   pages gets an overlapping GPU address (softpin at the CPU address). Timing-dependent: with a sleeping wait 2 of 4 runs failed,
   with `clFinish` 6 of 6 passed, it does not reproduce under gdb. The debug keys `EnableGemCloseWorker=0`,
   `EnableAsyncDestroyAllocations=0`, `EnableDeferredDeleter=0` (via `NEOReadDebugKeys=1`) reduce but do not remove it (7 of 8 runs pass).
   Map/unmap of a zero-copy buffer before releasing it also caused aborts (virtual events with references).
3. `CL_MEM_USE_HOST_PTR` on the interior of a USM host allocation ignores the offset (the start of the allocation is used): a silent
   wrong result.
4. The registration of host memory costs ~10 ms of CPU per 64 MB (as much as a copy).

The library avoids all of this by using USM host memory (`clHostMemAllocINTEL`) in the NEO builds and i915 userptr in the default build.
